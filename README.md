# Inventory ERP

## Requirements

- Python 3.10 or newer
- PostgreSQL
- Node.js 20 or newer

## First-time setup

Run commands from the repository root unless a step says otherwise.

1. Create an empty PostgreSQL database (the example name is `inventory_erp`). For example, if PostgreSQL command-line tools are on your PATH:

   ```bash
   createdb inventory_erp
   ```

2. Create and activate a Python environment, then install backend dependencies:

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   python -m pip install -r requirements.txt
   ```

3. Create the local environment file and edit it with your PostgreSQL credentials and a long, random JWT secret:

   ```bash
   cp .env.example .env
   ```

   Set `DATABASE_URL` in SQLAlchemy format, for example `postgresql+psycopg2://USER:PASSWORD@localhost:5432/inventory_erp`. Keep the actual `.env` private. On local HTTP, leave `COOKIE_SECURE=false`.

4. Create the database schema from the versioned migrations:

   ```bash
   alembic upgrade head
   alembic current
   ```

   The current revision includes the storefront checkout migration.

5. Create the first administrator account:

   ```bash
   python scripts/create_account.py
   ```

   Select `admin`, then enter the account details. This script creates or repairs the selected Admin, Manager, or Staff account. Do not use it to create accounts for ordinary public users; those register through the website.

## Online ordering and payments

Registered `user` accounts can browse products, add them to a cart, enter a delivery address, pay using SSLCommerz, and view order/tracking status under **My Orders**. The API calculates prices from the product catalog, reserves stock from one warehouse, and releases the reservation if payment fails or is cancelled. Admin/Manager/Staff create a shipment for paid online orders (or COD orders); tracking status is shown to the customer.

Set the following in the backend `.env` file:

```dotenv
SSLCOMMERZ_STORE_ID=your_store_id
SSLCOMMERZ_STORE_PASSWORD=your_store_password
SSLCOMMERZ_MODE=sandbox
FRONTEND_BASE_URL=https://your-store.example
PUBLIC_API_URL=https://api.your-store.example
DELIVERY_FEE_BDT=0.00
```

`PUBLIC_API_URL` must be publicly reachable over HTTPS because SSLCommerz calls the success/fail/cancel and IPN endpoints. Start with sandbox credentials and switch `SSLCOMMERZ_MODE=live` only when the merchant account is enabled for live payment. The API validates gateway transaction, BDT currency, and exact amount before recording payment or issuing an invoice.

Invoice email is optional and uses SMTP. Configure `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, and `SMTP_FROM`; without those settings, orders and invoices still work, but email is skipped. Delivery fee defaults to zero, so configure it to your actual shipping policy before accepting orders.

6. Start the backend in the activated Python environment:

   ```bash
   uvicorn app.main:app --reload
   ```

7. In a second terminal, configure and start the frontend:

   ```bash
   cd frontend
   npm ci
   cp .env.example .env.local
   npm run dev
   ```

8. Open `http://localhost:3000`, sign in as the administrator, and use **User Management** to create Manager and Staff accounts. Keep using `localhost` consistently so the browser sends the auth cookie to the API.

## Existing database

Back up an existing database before changing its schema. If it already tracks Alembic revisions, run `alembic upgrade head`. If it was created by the old application's `create_all()` startup and has no `alembic_version` table, do not run the fresh-database upgrade on it: first confirm that its schema matches the current models, then mark it with `alembic stamp head`. If the schema is not current, use a database-specific migration plan after making a backup.

## Routine migration workflow

After changing a SQLAlchemy model, generate and review a migration, then apply it:

```bash
alembic revision --autogenerate -m "describe the schema change"
alembic upgrade head
```

Review every autogenerated migration before applying it, especially when it drops or renames columns. The app does not create tables on startup; apply migrations before starting the backend.

## Production deployment checklist

- Terminate HTTPS at a trusted reverse proxy or hosting platform. Set `ENVIRONMENT=production`; this makes the API require a 32-character `JWT_SECRET_KEY` and defaults `COOKIE_SECURE=true`. Keep `COOKIE_SECURE=true` in production.
- Set `CORS_ORIGINS` to the exact frontend origin(s), comma-separated, such as `https://erp.example.com`. Do not use `*` with credentialed cookies.
- Set the frontend `NEXT_PUBLIC_API_URL` to the public HTTPS API origin before building the frontend. Build with `npm run build`; the project uses Next's Webpack build option to avoid the local Turbopack process permission failure.
- Store `DATABASE_URL` and `JWT_SECRET_KEY` in the deployment provider's secret/environment settings. Do not commit `.env` or place secrets in frontend variables.
- Schedule regular backups and test restoring them. For a manual backup, install PostgreSQL client tools and run from the repository root:

  ```bash
  source .venv/bin/activate
  python scripts/backup_database.py
  ```

  The script writes a timestamped PostgreSQL custom-format dump under `backups/` with private directory/file permissions. `BACKUP_DIR` can select another destination. Keep an off-host copy; a backup on the same machine is not sufficient for disaster recovery.

## Authentication and role checks

See [docs/ROLE_PERMISSIONS.md](docs/ROLE_PERMISSIONS.md) for the role matrix. Use `/users` as an Admin to create and manage operational accounts. Public registration creates only the `user` role.

## Automated API checks

Install development test dependencies and run the auth/role integration checks with an isolated in-memory SQLite database:

```bash
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
pytest
```
